# URL Shortener Engineered for Load

A link shortener where the app itself is deliberately trivial - create, redirect, stats
- because the actual point is the engineering report: what broke first under load, what
each fix bought, and honest numbers for all of it. This one runs on real Postgres and
real Redis; having built a Redis server from scratch for a sibling project is what made
the cache-aside layer here a five-minute decision instead of a researched one.

## Architecture

```
                 cache hit (~1ms)
   client --> FastAPI --> Redis --------------> 302 redirect
                 |            \
                 | cache miss  \-- buffered click count (async, off the hot path)
                 v
              Postgres (short_code, indexed)
```

Postgres is the source of truth (`links`: id, short_code, long_url, click_count).
Redis does two unrelated jobs: cache-aside for the redirect lookup, and a buffer for
click counts so the redirect response never waits on a Postgres write. Three env flags
(`SKIP_SHORT_CODE_INDEX`, `DISABLE_CACHE`, `SYNC_CLICKS`) let me reproduce any earlier
phase's exact behavior on demand - the numbers below all came from actually running
each configuration, not from memory of what a fix "should" do.

## Methodology

Docker Compose (app + Postgres 16 + Redis 7) on one Windows machine, 8 cores, load
generated by Locust running on the same host - client and server share hardware here,
so treat the *relative* jumps between rows as the finding, not the absolute req/s.
1,024,865 links seeded via `COPY` before any measurement. Each run: 50 users, spawn
rate 10/s, 30s, one run per row (not averaged - see "what I'd do next").

## Baseline

| Scenario | req/s | p50 | p95 | p99 |
|---|---|---|---|---|
| redirect | 100 | 480ms | 650ms | 750ms |
| create | 782 | 55ms | 70ms | 85ms |
| mixed 95/5 | 88 | 540ms | 790ms | 930ms |

Redirects are the slow path by design: Phase 1's schema has no index on `short_code`,
so every redirect is a sequential scan over a million rows.

## Optimizations (redirect scenario, each row builds on the last)

| Change | req/s | p50 | p95 | p99 |
|---|---|---|---|---|
| + index on `short_code` | 978 | 34ms | 68ms | 87ms |
| + Redis cache-aside | 1035 | 34ms | 64ms | 93ms |
| + buffered clicks (off hot path) | 874 | 33ms | 77ms | 110ms |

The index is the whole story - `EXPLAIN ANALYZE` on the same query went from a
16.4ms parallel sequential scan (1M rows filtered) to a 0.04ms index scan, and
throughput jumped ~10x. The cache barely moved the needle on top of that: at this
concurrency, Postgres with an index was already fast enough that Redis wasn't the
bottleneck anymore. I tested that suspicion by running the cached config with 4
uvicorn workers instead of 1, expecting more throughput - it got *worse* (724 req/s),
most likely from each worker opening its own 20-connection Postgres pool while
competing with Locust itself for the same 8 cores. I didn't chase that further since
proper horizontal scaling needs the load generator on separate hardware to mean
anything - noted below.

Moving clicks off the hot path didn't show a clean win either: p50 is a wash (33ms vs
34ms) and buffered actually ran slightly slower on this single run (874 vs 1035
req/s). I take the p50 result at face value - the spec's actual claim ("redirect
latency with counting on and off should be about equal") holds - and read the
throughput gap as noise from sharing 8 cores across Locust, the app, Postgres, and
Redis rather than a real regression; a second run would be needed to be sure. The
architectural win is real regardless of the noise: the redirect path never blocks on
a Postgres write, and if that write ever gets slow under real production load, the
redirect stays fast either way.

## Short codes and consistency

Counter+base62 short codes, coordinated by a Postgres sequence - zero collisions,
zero retries, by construction. The honest tradeoff: codes are sequential, so they're
enumerable (`shorten.example/G8`, `G9`, `GA`, ...). I chose it anyway because
collision-free simplicity was worth more here than obscurity, but a production system
that cared about scraping would want random-with-retry or an obfuscation layer instead.

Click counts are eventually consistent: buffered in Redis, flushed to Postgres every 5
seconds. A crash between a click and the next flush loses that click - Redis isn't
used durably here. That's the trade for keeping every redirect's response free of a
synchronous write.

## What I'd do next

Average multiple runs instead of citing single ones (the buffered-clicks result above
is the clearest place this would help). Run the load generator on a separate machine
from the app, which is the only honest way to test whether more uvicorn workers or a
second app instance actually helps. And a real production system would need an
enumeration-resistant short code before shipping - noted above, deliberately not fixed.

## Running it

```
docker compose up -d --build              # app + postgres + redis
python src/seed.py                        # ~1M links, writes load/seeded_codes.txt

pip install -r requirements.txt
pytest                                    # needs postgres+redis up (see tests/test_api.py)

locust -f load/locustfile_redirect.py --host http://localhost:8000 --headless -u 50 -r 10 -t 30s
locust -f load/locustfile_create.py   --host http://localhost:8000 --headless -u 50 -r 10 -t 30s
locust -f load/locustfile_mixed.py    --host http://localhost:8000 --headless -u 50 -r 10 -t 30s
```
